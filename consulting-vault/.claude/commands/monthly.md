# /monthly — 月次の資料生成

引数: `$ARGUMENTS`（`YYYY-MM`。空なら前月）

このコマンドは vault ルート（`CLAUDE.md` がある場所）で実行する。以下の手順を上から順に、省略せずに実行すること。

## 絶対に守るルール（CLAUDE.md の要点）
- **sources 外の情報を書かない。** 書く前に読むファイルを決めて frontmatter の `sources:` に並べ、そのファイルの内容だけで書く。記憶・一般論・他クライアントの情報で補わない。
- **書けない項目は「要確認」。** 見出しは残し、それらしい文で埋めない。
- **数字はソースにあるものだけ。** 根拠のない効果は「要試算」。Claude が試算する場合は「試算（仮定: …）」と明記し、仮定をすべて書く。
- **文体は各クライアントの `_profile.md` の `style:` に従う。**（空なら「です・ます調。簡潔に。」）
- **frontmatter とフッターの形式は CLAUDE.md（データ契約6章）どおり。** `type` / `client` / `date` / `generated_at` / `sources`（ブロックリスト、クライアントフォルダからの相対パス）。本文末尾に空行→`---`→`本資料は以下の記録から作成: [[ファイル名]] / [[ファイル名]]`（拡張子なし、sources の全ファイル）。
- テンプレートの見出しと順番を変えない。`<!-- 書き方 -->` コメントと `{{ }}` は生成物に残さない。
- **`raw/` と `sent/` には絶対に書き込まない**（編集・上書き・削除・移動もしない）。`_profile.md` と `02_templates/` も書き換えない。
- 生成物（`YYYY-MM/` 配下の `sent/` 以外）は既にあっても上書きしてよい。

## 手順

### 0. 準備
1. `date "+%Y-%m-%d"` を実行して今日の日付を確認する。
2. 対象月を決める。`$ARGUMENTS` が `YYYY-MM` 形式ならそれ、空なら今日の前月。形式が違えば実行を止めて利用者に聞く。以下 `<月>` と書く。
3. `CLAUDE.md` を読む。
4. `01_clients/*/_profile.md` を全部読み、各クライアントの `client` / `style` / 目標KPI / 注意点を把握する。

### 1. 稼働ログの土台を作る
`python3 03_scripts/worklog.py <月>` を実行する。
- 「記録なし」と出たクライアントは、以降の手順（2〜7）をすべて飛ばす。
- エラーが出たらスクリプトを書き換えずに止め、エラー内容を利用者に報告する。

### 2. raw を読む
クライアントごとに、`01_clients/<client>/raw/` のうち frontmatter の `date` が `<月>` のファイルを**全部**読む（一覧は `<月>/worklog.md` の `sources:` と同じ）。

### 3. 議事録（会議ごと）
`type: meeting` の raw 1件につき1ファイル、`02_templates/minutes.md` に従って作る。
- 保存先: `01_clients/<client>/<月>/minutes/YYYY-MM-DD_<会議名>.md`
- sources: その会議の raw（`raw/…`）。
- 文字起こしに無い決定事項・発言を書かない。提案・助言には該当タイムスタンプを添える。

### 4. 提案書（実際に提案したものだけ）
会議・チャットで**コンサルタントが実際に提案した内容**がある場合だけ、提案1件につき1ファイル、`02_templates/proposal.md` で作る。
- 保存先: `01_clients/<client>/<月>/proposals/YYYY-MM-DD_<テーマ>.md`
- sources: 元の議事録（`<月>/minutes/…`）または raw のチャット。背景に `_profile.md` を使ったら `_profile.md` も加える。
- 発言・メッセージに無い提案を作らない。該当が無ければ作らない（0件で正常）。

### 5. Q&A（相談1件1ファイル）
`type: slack` / `line` / `mail` の raw に含まれる相談ごとに、`02_templates/qa.md` で作る。
- 保存先: `01_clients/<client>/<月>/qa/YYYY-MM-DD_<テーマ>.md`
- sources: その相談の raw。雑談・日程調整だけのやり取りは Q&A にしない。
- 回答していない部分を補わない。回答がソースに無ければ「未回答（要確認）」。

### 6. 稼働ログの仕上げ
`01_clients/<client>/<月>/worklog.md` を編集する。
- 書き直してよいのは **「要点」列と「作業分類」列だけ**。raw の中身を読んで、要点は1行・40字以内、作業分類は 準備 / 会議 / 調査 / 提案 / 相談対応 / フォロー / 資料作成 のどれか1つ（判断できなければ「要確認」）。
- **日付・種別・相手・所要目安（推定）・ソースの各列、行の数と順番、「月末集計（推定）」、推定根拠、frontmatter、フッターは一切変えない。**（機械算出値。数字を直したいときは利用者に報告する）

### 7. 月次レポート
`02_templates/report.md` で `01_clients/<client>/<月>/report.md` を作る。
- sources: `<月>/worklog.md` と、手順3〜5で作った `<月>/minutes/…` / `<月>/proposals/…` / `<月>/qa/…` の全部。KPI の目標値に `_profile.md` を使ったら `_profile.md` も、KPI 実績値に raw を使ったらその raw も加える。
- 稼働サマリーの数字は worklog.md の「月末集計（推定）」と一致させ、「（推定）」を付ける。
- 原則 raw を直接読まず、生成済みの資料から書く。

### 8. 根拠の検査
`python3 03_scripts/check_sources.py <月>` を実行する。
- ERROR が出たら該当ファイルを直して再実行する。**ERROR が0件になるまで繰り返す。**
- 直し方: 存在しないパスは正しいパスに直すか sources から外す。外したソース由来の記述は本文からも消し、必要なら「要確認」にする。フッター欠落はフッターを足す。**ERROR を消すためにソースを新しく作ったり、raw/ や sent/ を触ったりしない。**
- 同じ ERROR が3回直しても消えない場合は、そこで止めて利用者に報告する。
- WARN（リンク切れ等）は直せるものは直す。INFO（要確認・要試算の数）は直さずに報告に回す。

### 9. 報告
最後に、次の形で利用者に報告する（ファイルの中身を全文貼らない）。
1. **クライアント別の生成ファイル一覧**（worklog / minutes / proposals / qa / report。記録なしのクライアントも「記録なし」と明記）
2. **要確認・要試算の件数と箇所**（check_sources.py の INFO をファイル名と行番号で）
3. **利用者がレビューで見るべき点**（例: 推定時間が体感とズレていないか、提案書の元発言、KPI 実績値が未受領、決定事項か未確定か迷った箇所、今月やったのに記録が無さそうなこと）
4. check_sources.py の最終結果（ERROR 0 であること）
